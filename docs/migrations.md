# Schema migrations

From v0.5 the schema has a history: Alembic migrations in [`testamur/migrations/`](../testamur/migrations/), run by
`testamur db upgrade` (the Compose stack's `migrate` service runs it before the API and the worker start). The service
refuses to start on a database whose revision is not the code's (`/readyz` reports both).

| Revision | What it does |
|---|---|
| `0001` | Every table of the store and the job queue, as the models define them: composite foreign keys on (tenant, id), deferred so the unit of work can insert in any order. |
| `0002` | Postgres only (a no-op on SQLite): row-level security on every tenant table for the application role (`testamur_app`, or `TESTAMUR_APP_ROLE`), the role created without a login if the deployment has not made it. The tables are listed in the revision itself, so it means the same thing after later revisions add tables. |

Rules a new revision follows, each held by a test in [`tests/test_migrations.py`](../tests/test_migrations.py):

- **The migrations build exactly the models.** An empty database brought to head compares equal to the models
  (Alembic's `compare_metadata` finds nothing), and comes back down to an empty schema.
- **A new tenant table brings its own row-level security.** A revision that adds a table with a `tenant_id` lists it
  in its own `RLS_TABLES` and installs the policy (`testamur.store.rls_statements`); a test fails while any tenant table
  is covered by no revision.
- **On Postgres the migrations alone isolate tenants.** The Postgres CI job migrates a fresh schema and checks, as the
  application role, that one firm's session cannot see another firm's rows.

Generating a revision after a model change:

```bash
python -c "from alembic import command; from testamur.migrations import config; command.revision(config('sqlite:///data/gen.db'), message='what changed', autogenerate=True)"
```

on a database already at head (`testamur db upgrade --url sqlite:///data/gen.db` first), then read the generated file:
autogenerate does not see everything (a changed server default, a renamed column) and a data migration is written by
hand.

## Databases from before v0.5

Before v0.5 the store created its tables itself (`create_all`), and the databases it made hold synthetic worlds only.
They have no revision and are not upgraded: rebuild them from their world (`testamur harness`, `testamur demo seed`).
Tests and the harness still create their throwaway databases directly (`Store(create_schema=True)`, the default);
the service never does.

## The workflow's checkpoints

LangGraph's checkpoint tables are LangGraph's, created and migrated by its own saver (`PostgresSaver.setup()`), which
`testamur db upgrade` runs when `TESTAMUR_CHECKPOINTS` names a Postgres database. They hold no tenant column: a
checkpoint is reached only through its run's thread id, which is generated by the platform and read only inside the
run's tenant session.
